# Python Tool 自动发现与注册指南

## 1. 解决的问题

平台不再要求每开发一个 Python Tool 就追加一条精确白名单。部署负责人
只需批准可信代码包，平台启动时自动发现其中合规的 `BaseTool`，管理员
再从 Tool 管理界面选择、创建版本并发布。

## 2. 配置

```yaml
tool_python_discovery_packages:
  - company_tools
```

`tool_python_discovery_packages` 是代码信任边界。不要填写第三方依赖根包、
用户上传目录或可被普通用户写入的目录。

## 3. Tool 进入候选目录的条件

- 类继承 `BaseTool`；
- 类定义在被扫描模块中，而不是从其他模块导入；
- 支持零参数构造；
- `name` 在所有候选 Tool 中唯一；
- `schema()` 可以在启动阶段正常生成。

任一可信包无法导入、Tool 无法构造或名称重复时，错误组件不会进入运行
时，管理端会展示明确原因，避免错误被静默忽略。

当前实现采用故障隔离：扫描失败的包或组件会记录在发现错误中；已发布
Tool 如果在新部署中缺失、无法构造、名称变化或输入 Schema 漂移，会在
数据库中标记为 `unavailable` 并记录 `runtime_error`。平台和其他 Tool
继续启动，故障 Tool 不会进入 `ToolRegistry`，因此 Agent 无法调用它。

## 4. 完整流程

```text
开发 Tool → 部署代码 → 重启服务扫描可信包
        → 候选组件目录 → 管理员创建 Tool 版本
        → 审核风险策略 → 发布到 ToolRegistry
        → AgentConfig 按 Tool 逻辑名称授权调用
```

候选目录接口为 `GET /v1/tool-components/python`。它只返回部署时发现的
组件元数据，不接收代码或任意 Python 路径。

## 5. 三层安全边界

1. **部署边界**：只有可信包内的代码能成为候选；
2. **注册边界**：只有管理员选择并发布的候选进入 `ToolRegistry`；
3. **Agent 边界**：Agent 只能调用自身 `tools` 列表授权的逻辑 Tool。

因此，Tool 注册中心解决“哪些已部署能力可上线”，Agent Tool 列表解决
“某个 Agent 可以调用哪些已上线能力”。两者职责不同，不能互相替代。

## 6. 变更影响

包内新增 Tool 不需要修改配置，但仍需要部署代码并重启服务完成扫描。
如果新增的是一个全新的业务包，需要由部署负责人把该包加入可信包列表。

## 7. 修改已发布 Tool 的正确方式

不要直接删除或破坏线上版本对应的类。修改 Tool 输入 Schema、名称或模块
路径时，应创建新的 Tool 版本，完成测试后再发布。纯内部实现变更也建议
升级代码版本并完成回归评测，以便部署、审计和回滚记录保持一致。
