# 企业级 AI Agent 平台架构搭建与源码导读

本文不是功能清单，而是解释平台为什么这样搭、每一层如何实现，以及阅读源码时应从哪里进入。

## 一、先记住三条主线

### 1. 启动装配线

```text
run.py
→ Bootstrap.build
→ 读取环境配置
→ 创建基础设施 Adapter
→ 扫描 Agent / Prompt / Tool / Workflow 文件包
→ 注册到各 Registry
→ 创建 Dispatcher、Executor、Runtime
→ Application 注册 HTTP 路由与生命周期
```

关键源码：

- `run.py`：只负责创建 Bootstrap 并启动，不包含业务注册。
- `app/bootstrap/config.py`：配置 Interface 与默认值。
- `app/bootstrap/configuration_mixin.py`：按环境加载、合并、校验配置。
- `app/bootstrap/bootstrap.py`：组合根，决定对象如何创建和连接。
- `app/core/container/`：保存按类型或名称解析的依赖。
- `app/bootstrap/registry_loader.py`：把持久化配置投影加载到运行时 Registry。
- `app/agent/packages.py`：扫描文件化 Agent 包并生成运行时快照。
- `app/bootstrap/application.py`：持有最终应用并控制启动/停止顺序。

Bootstrap 是装配者，不参与请求执行；Container 解决依赖获取，Registry 解决业务资源按名称查找。

### 2. 用户入口选择线

```text
智能助手 → AIApplicationRouter 自动选择应用 ┐
专业工作台 → 指定 Application              ├→ AIApplicationExecutor
固定表单 → 指定 Application                ┤
外部 API → 指定 Agent / Workflow / Application ┘
→ Runtime 或 WorkflowExecutor
```

关键源码：

- `app/ai_application/router.py`：依据已发布应用的路由规则做可审计选择。
- `app/ai_application/executor.py`：屏蔽 Agent 与 Workflow 执行差异。
- `app/bootstrap/routes/ai_application.py`：应用目录、刷新、指定执行和智能执行接口。
- `applications/*/application.yaml`：页面模板、菜单、权限、输入 Schema 和路由规则。

Application 只定义产品入口，不实现 Agent 推理。不同入口选中目标后仍复用下面的
Runtime、权限、任务、Trace、Memory 和审计链路。

## 二、同步请求执行线

```text
HTTP POST /v1/agents/run
→ Application：认证、授权、限流、审计、请求转换
→ Runtime.run：建立 RuntimeContext、Trace、根 Span
→ MiddlewareManager：输入安全和横切治理
→ Runtime Executor：统一执行、异常映射、事件记录
→ Dispatcher：按 agent 名称选择执行目标
→ AgentExecutor：创建 AgentContext 并守住 Agent 执行边界
→ BaseAgent / LLMAgent：执行业务
→ AgentResult
→ Runtime 收尾 Trace、Metrics、审计
→ HTTP JSON
```

对应源码阅读顺序：

1. `app/bootstrap/routes/agent.py`
2. `app/runtime/runtime.py`
3. `app/runtime/middleware.py`
4. `app/runtime/executor.py`
5. `app/runtime/dispatcher.py`
6. `app/agent/executor.py`
7. `app/agent/base.py`

设计理由：Runtime 只认识统一请求和执行目标，不知道天气、旅行等业务；Dispatcher 只路由；
AgentExecutor 统一注入依赖与处理错误；真正业务行为留在 Agent。

## 三、LLMAgent 内部能力线

```text
LLMAgent.execute
├─ MemoryManager.load_context：加载会话窗口、摘要和语义记忆
├─ AgentKnowledgeContext.build：按知识库配置执行 RAG
│  ├─ Embedding
│  ├─ Milvus 检索
│  └─ Reranker 重排
├─ PromptRegistry.get：获取本次运行快照
├─ PromptTemplate.render：校验并渲染 Jinja2 变量
├─ LLMManager.chat：模型路由、超时、重试、用量记录
├─ AgentToolRound.execute：解释模型 ToolCall
│  └─ ToolExecutor.execute：授权、Schema、审批、幂等、熔断、沙箱
├─ 重复 LLM / Tool 回合，直到得到最终回答或达到上限
└─ MemoryManager：保存对话并提取有价值的长期记忆
```

核心模块：

- `app/memory/manager.py`：对外只暴露记忆加载和保存语义，隐藏存储差异。
- `app/agent/knowledge_context.py`：把 RAG 复杂度封装成构建知识上下文。
- `app/prompt/registry.py`、`template.py`：Prompt 查找、变量校验、渲染。
- `app/llm/manager.py`、`routing.py`、`resilience.py`：多模型路由和韧性。
- `app/agent/tool_round.py`：控制一次模型工具回合。
- `app/tool/executor.py`：所有 Tool 必须经过的治理入口。

## 四、异步任务与故障恢复线

```text
POST 提交任务
→ PostgreSQL runtime_tasks（queued）
→ RuntimeWorker.claim（FOR UPDATE SKIP LOCKED）
→ 写入 worker、lease_token、lease_expires_at
→ Runtime.resume 恢复 Context 与 Trace
→ 后台执行并持续 heartbeat
→ runtime_task_events 追加事件
→ completed / failed / cancelled
```

关键源码：

- `app/runtime/task.py`：任务 Interface 与 TaskManager。
- `app/runtime/persistence.py`：PostgreSQL Adapter、租约和 fencing 校验。
- `app/runtime/worker.py`：抢占、心跳、执行、失租处理与重试。
- `runtime_worker.py`：独立进程入口。
- `app/bootstrap/routes/health_runtime.py`：任务查询、取消和 SSE 增量事件。

租约解决 Worker 崩溃后的恢复；`lease_token` 防止旧 Worker 恢复后覆盖新 Worker 的结果；
事件独立成表使前端只按游标读取新增事件。

## 五、文件资源与运行时快照

```text
agents/<package>/agent.yaml
├─ prompts/*.yaml + *.jinja2
├─ tools/*.py
└─ agent.py（可选）
        ↓ 扫描、校验、实例化
AgentPackageManager
        ↓ Prompt 原子替换；Agent 在依赖可用后激活
PromptRegistry / AgentRegistry
        ↓
下一次请求取得新快照
```

Python Tool 的扫描与发布是另一条受控链：可信包扫描只生成候选，不等于直接执行；管理员
在 Tool 管理创建、审核并发布版本后，配置记录进入 PostgreSQL，启动时由 RegistryLoader
恢复为 ToolRegistry 运行时实例。这样“部署代码可信”和“业务允许启用”是两道独立控制。

源码由 Git 管理，数据库保存配置投影、评测报告、任务、Trace、用量和审计，不重复保存
Python/Jinja2 正文。开发环境允许文件写入和热加载；生产环境 `agent_workspace_writable=false`，
通过 Git commit 和部署制品保证可追溯。

## 六、Workflow 与 Agent 的分工

```text
确定性、可审计的业务顺序、条件、循环、审批、补偿
→ WorkflowExecutor

开放问题理解、工具选择、内容生成
→ LLMAgent

跨平台远程 Agent 协作
→ A2A Adapter

外部标准工具接入
→ MCP Adapter → ToolRegistry → ToolExecutor
```

Workflow 源码位于 `app/workflow/`，文件包位于 `workflows/`。MCP 和本地 Python Tool
最终都适配为统一 Tool Interface，因此授权、审计和 Trace 不会出现两套逻辑。

## 七、基础设施 Adapter

| 能力 | Interface | 生产 Adapter | 开发/测试 Adapter |
|---|---|---|---|
| 任务与业务数据 | Store/Manager | PostgreSQL | 内存或 SQLite（局部） |
| 短期记忆 | BaseMemoryStore | Redis/PostgreSQL | InMemoryStore |
| 语义记忆与知识库 | BaseVectorStore | Milvus | 测试 Fake |
| Tool 状态 | ToolStateStore | Redis | InMemoryToolStateStore |
| 对象文件 | 对象存储 Interface | MinIO | 本地测试实现 |
| 模型 | BaseLLM/能力 Interface | OpenAI 兼容 Provider | 测试 LLM |

这些 seam 只有在确实存在两个 Adapter 时才保留，使业务层不依赖具体数据库客户端。

## 八、一次完整调试路线

建议用 `weather-agent` 设置以下断点：

1. Agent HTTP 路由接收请求。
2. `Runtime.run` 创建 Context。
3. `Executor.execute` 进入统一执行边界。
4. `Dispatcher.dispatch` 查找 Agent。
5. `AgentExecutor.execute` 构建 AgentContext。
6. `LLMAgent.execute` 加载 Memory。
7. `AgentKnowledgeContext.build` 检索知识。
8. Prompt 获取与渲染。
9. 第一次模型调用产生 ToolCall。
10. `ToolExecutor.execute` 后进入业务 Tool。
11. 第二次模型调用生成答案。
12. Memory 保存、Trace 和事件收尾。

再用异步任务接口调试 `TaskManager → RuntimeWorker → Runtime.resume`，最后用
`travel-collaboration` 调试 Workflow。这样能依次理解单请求、后台执行和多 Agent 编排。

## 九、判断一个新能力应该放在哪里

- 请求级横切治理：Runtime Middleware。
- 新模型厂商：LLM Adapter，不改 Agent。
- 新本地能力：Agent 包下 Tool，通过 Registry 注册。
- 外部工具协议：MCP Adapter。
- 会话信息：Memory；企业资料：Knowledge。
- 固定业务流程：Workflow。
- 远程 Agent：A2A Adapter。
- 对象创建和连接：Bootstrap。
- 按名称发现资源：Registry。
- 依赖实例解析：Container。

如果一个业务模块开始直接创建数据库、模型客户端、Registry 或 Runtime，通常说明它越过了正确的 seam。
