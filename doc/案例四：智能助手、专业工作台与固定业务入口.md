# 案例四：智能助手、专业工作台与固定业务入口

本案例说明同一个 Agent 如何通过不同产品入口使用，而不复制 Runtime 执行逻辑。

## 一、案例资源

```text
agents/weather_agent/                         # Agent 执行能力
agents/multi_tool_trip_agent/                 # 多 Tool Agent
applications/weather_assistant/application.yaml  # 专业聊天工作台
applications/travel_planner/application.yaml     # 固定旅行规划表单
```

## 二、三种前台使用方式

### 1. 智能助手

访问 `/assistant`，输入“杭州明天会下雨吗”。平台根据应用中的 `routing` 配置选择
`weather-assistant`，再由应用执行器调用 `weather-agent`。

```text
用户自然语言
→ AIApplicationRouter
→ weather-assistant
→ AIApplicationExecutor
→ Runtime
→ weather-agent
```

### 2. 专业 Agent 工作台

从“AI 应用 → 天气助手”进入。`presentation.template: chat` 决定使用聊天界面，
`target.name: weather-agent` 决定执行对象。

### 3. 固定业务入口

从“AI 应用 → 旅行规划”进入。`presentation.template: form_result` 根据
`input_schema` 生成目的地、天数、人数和偏好表单，提交后调用
`multi-tool-trip-agent`。如果目标改为 Workflow，前端无需重写执行代码。

## 三、应用文件关键字段

```yaml
name: travel-planner
status: published
target:
  type: agent
  name: multi-tool-trip-agent
presentation:
  template: form_result
menu:
  enabled: true
  title: 旅行规划
security:
  permission: business:travel:use
routing:
  enabled: true
  keywords: [旅行, 行程, 景点, 预算]
  examples: [帮我规划杭州三日游]
  priority: 100
input_schema:
  type: object
  properties:
    destination:
      type: string
      title: 目的地
      default: 杭州
```

## 四、四种 API 调用方式

```text
POST /v1/assistant/execute                         # 自动选择应用
POST /v1/applications/{application_name}/execute # 指定产品入口
POST /v1/agents/run                               # 指定 Agent
POST /v1/workflows/{workflow_name}/executions    # 指定 Workflow
```

业务系统知道执行对象时，应使用明确调用；只有终端用户不知道选择哪个能力时，才使用
智能助手路由。

## 五、如何调试

1. 重启后端，使新增应用路由代码生效。
2. 在应用中心确认两个应用均已发布。
3. 分别从智能助手、天气工作台和旅行表单各执行一次。
4. 在任务追踪中比较入口节点。
5. 智能助手应显示“智能路由选择应用”。
6. 指定应用应显示“业务应用提交请求”。
7. 后续 Runtime、Agent、RAG、LLM、Tool 和 Memory 节点应保持一致。

## 六、职责边界

- Agent：解决“如何推理和使用能力”。
- Workflow：解决“固定步骤怎样可靠执行”。
- Application：解决“用户看到什么界面、允许谁访问、绑定哪个目标”。
- Router：解决“用户没有指定目标时选择哪个应用”。
- Runtime：解决“所有 Agent 请求如何可靠、可追踪地执行”。
